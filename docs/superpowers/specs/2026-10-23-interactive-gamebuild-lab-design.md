# ForgeRail · Game Build Engineering Lab 交互实验台设计

- 日期：2026-10-23
- 状态：待用户审阅；尚未开始产品代码实现
- 基线：公开仓库 `Epochex/ForgeRail`，`fec480888e3747b855731aa5af5655ea9cfdb59c`

## 1. 目标与用户要求

帮助用户准备 10 月 26 日的游戏构建开发面试。用户可以作为程序、美术、QA 或构建工程师，在浏览器中亲手制造故障、运行构建流程、阅读证据、实施修复和重新验证，理解整个交付过程。

本次交付包含前端、后端和场景化浏览器 E2E。只有一个工作台，16 个 case 在同一页面切换，每个 case 都有可执行的问题解决闭环，不设置只有介绍文字的空入口。默认从现有 ForgeRail 扩展，保留原有 CLI 和核心协议兼容性。

用户明确不需要实际运行 Unity：本次不启动、不安装、不激活 Editor，不启动真实 Unity Player，不启动 Jenkins、Docker 或平台 SDK。用户随后希望成功界面采用 Unity 构建成功的呈现方式：界面使用 Unity 流水线的阶段名称，主结果可写“构建成功”，同时紧邻结果保留可见的 `Lab` 标识；结构化报告始终为 `execution_mode: lab`。不生成虚假的 Editor/Player 日志，不将轻量实验描述为真实引擎执行。

成功标准：用户看完一次失败与修复，能够回答“谁做了什么修改、任务经过哪些环节、哪条证据说明失败、修复改变了什么、哪条断言证明修复有效”。

## 2. 实现方式与取舍

选用 **现有 FastAPI + 原生 ES Modules / HTML / CSS 单页 + Python 场景执行器**。前端由 Python 服务直接提供，浏览器与 API 同源；安装既有 Python 依赖后，一条命令启动，不新增前端构建工具和应用 UI 依赖。

备选为 React + Vite：适合后续大量页面与组件扩展，但本次只有一个工作台，增加打包、安装和双服务联调成本。此设计选择原生模块，通过拆分视图、数据访问和状态管理保证可维护性。

仅本机运行，使用现有 checkout，不建立或发布托管 Site。真实 Git 操作、本地文件、进程树与 SQLite 是实验必要条件。

## 3. 工作台布局

桌面布局分为三部分：

1. 左侧场景栏：16 个 case，按资源、协作、构建、效率、节点、环境、交付分组；提供搜索、角色筛选和完成状态。角色用于学习路径，不代表权限系统。
2. 中间主区：场景目标、事故背景、影响、故障变体选择、操作步骤和阶段流程图。顶部一眼能看到当前版本、任务状态与下一步操作。
3. 右侧证据栏：当前步骤的输入/输出、文件 diff、命令/退出码、结构化断言和日志。窄屏转为主区下方的可切换面板。

底部提供实测阶段时间线、失败/修复前后对比和历史执行选择。流程图节点可点击，定位对应阶段和证据。日志按阶段展示，原始内容可展开，不默认用大段日志遮住解释。

视觉方向：深石墨色工作台、浅色正文、橙色交互强调，成功/警告/失败使用独立语义色。中文系统字体配等宽证据文本；以“阶段节点与证据联动”作为核心视觉交互。使用真实状态变化驱动更新，不依靠计时器播放假进度。支持键盘焦点、文字状态、移动宽度和减少动态效果偏好。

场景切换不创建新页面，地址使用 `#case=<id>&run=<id>` 保留选中状态。刷新后重新获取后端记录。加载中、尚未执行、接口失败、执行异常和中断状态都有明确提示。

## 4. 每个 case 的统一闭环

每个 case 必须包含：背景/角色、输入基线、故障变体、实际影响、预期失败点、真实执行、诊断依据、修复动作、修复 diff、复验断言、前后结果对比、面试追问和验证边界。

交互顺序：

`创建独立实验 → 制造问题 → 执行流程 → 查看诊断 → 应用修复 → 重新验证 → 对比结果`

每一步按钮触发后端动作，返回动作 ID；浏览器轮询事件与状态，展示实时产生的记录。常用入口“完整演练”依次调用相同动作接口，允许停止，保留每个步骤的证据，不走另外一套预录结果。

诊断必须引用实际 rule ID、文件路径、日志行、退出码或 HTTP 响应。修复必须修改实验文件、Git 提交、节点能力、缓存、任务或发布状态；不能只更改 UI 状态或塞入预设成功 JSON。

结果分层：

- 执行结果：`QUEUED / RUNNING / SUCCEEDED / FAILED / CANCELLED / BLOCKED / INTERRUPTED`。
- 学习闭环：`未开始 / 问题已复现 / 已诊断 / 已修复待验证 / 复验通过`。
- 期望失败被观测到时，界面显示“问题已复现”，保留构建阶段的失败状态；只有修复后的实际断言全部通过，才显示“复验通过”。
- 普通用户主动停止实验标为取消，不算修复成功。预期能力不足可作为 case 的正确观测结果，但不能算出包成功。

## 6. 后端结构与复用边界

新增 `src/gamebuild/lab/`：

- `catalog.py`：场景、角色、变体、步骤、诊断/修复说明和断言元数据。元数据只解释执行结果，不持有预设的成功结果。
- `api.py`：同源工作台接口、静态资源、认证和生命周期管理。
- `store.py`：Lab 会话、动作与事件 SQLite；和原控制面任务账分开保存，避免破坏原表结构。
- `service.py`：动作状态校验、幂等请求、并发额度、执行/取消和恢复。
- `runner.py`：独立 Python 动作执行进程、结构化事件写入、阶段耗时与证据登记。
- `fixtures.py` 与分组场景模块：只在当前实验目录内创建小型 Git 工程、资产与运行程序，按 case 完成真实操作。
- `web/`：`index.html`、CSS 和分开的 API/状态/场景/证据/时间线 ES modules。

优先复用 `source.py`、`checks.py`、`cache.py`、`preflight.py`、`runner.py`、`artifacts.py`、`store.py` 和 `diagnostics.py`。新增资源引用与内容更新模型明确为 Lab fixture 协议。现有 Lab worker 的 `smoke.json` 目前由 worker 写入，case 06 必须补充独立启动进程的回执，不能直接拿旧字段作为启动证明。

需要 HTTP 任务链的 case 启动短生命周期本地控制面和节点进程；动作完成后清理进程，保留状态库、日志和产物。各 case 拥有独立控制面数据目录。浏览器只调用 Lab API，不接触内部 worker token。

建议启动入口：`gamebuild lab --root runtime/interactive-lab --port 18766`。默认绑定 `127.0.0.1`，打印可打开的本机地址；命令停止后回收所属进程。保留原 `serve`、`worker`、`demo` 等行为。

## 7. 数据、API 与状态约束

数据保存在 `runtime/interactive-lab/`：Lab SQLite、每次 run 的 fixture Git、独立工作区、核心控制面数据、stdout/stderr、diff、断言报告和产物。生成内容不进 Git。

Lab 表结构至少包含：

- `runs`：ID、case、variant、创建时间、状态、当前阶段、上次动作、基线/修复 SHA。
- `actions`：ID、run、动作名、幂等键、状态、开始/结束时间、退出结果。
- `events`：递增序号、run/action、事件类型、阶段、时间、结构化正文。
- `evidence`：ID、run/action、类型、实验根内相对路径、大小、SHA256。

主要接口：

| 接口 | 用途 |
| --- | --- |
| `GET /lab/api/cases` | 场景目录、步骤、变体和验证边界 |
| `POST /lab/api/runs` | 创建独立实验，只接受登记的 case/variant |
| `GET /lab/api/runs` / `/{id}` | 历史与当前实验快照 |
| `POST /lab/api/runs/{id}/actions` | `prepare / inject / execute / diagnose / repair / verify`；202 返回动作 ID |
| `GET /lab/api/runs/{id}/events?after=<seq>` | 增量拉取实际事件，活动时约 500 ms 一次，空闲停止轮询 |
| `POST /lab/api/runs/{id}/cancel` | 停止当前动作与所属进程树，保留证据 |
| `GET /lab/api/runs/{id}/evidence/{evidence_id}` | 读取/下载受限证据或实际产物 |
| `GET /lab/api/runs/{id}/export` | 下载脱敏后的闭环 JSON 报告 |

每个 run 同时只允许一个变更动作；全局最多两个 case 执行。重复按钮/网络重试必须使用动作幂等键，不能生成重复副作用。状态越级请求返回 409 并说明允许的下一步。失败保留根因与证据，不把运行异常改成预期失败。

服务重启后把未完成动作标为 `INTERRUPTED`，保留之前事件和文件，允许新尝试；不展示永久旋转的假运行状态，不根据丢失的 PID 终止其他进程。重新开始创建新的 run，不静默删除旧证据。

## 8. 安全与成本约束

实验操作只使用登记的动作和参数，不提供任意命令、任意本机路径或任意网络 URL 输入。服务使用随机本机启动凭据建立 HttpOnly/SameSite 会话，浏览器端不硬编码原控制面 token。校验 Host/Origin，写接口需要同源会话；凭据不写日志或导出报告。

所有文件访问以实验根和证据登记为准，拒绝路径越界、链接穿透和未知证据 ID。资源规模、日志和动作时长设上限。所有实验子进程交由进程树管理，退出/取消负责清理。

单 case 的默认演练目标为数秒至几十秒；全部 case 的浏览器回归目标在本机数分钟量级。目标不作为尚未测量的承诺。没有通过长时间 sleep 人工凑出构建性能提升；小型工作负载的结果不外推到大型游戏。

## 9. 场景 E2E 与验收

用户明确要求场景化 E2E，因此提交可重复执行的 Playwright 浏览器测试文件，浏览器使用真实本地前后端，不 mock Lab HTTP 响应。另用 pytest 覆盖后端机制、非法状态和故障边界。先验证能复现失败，再验证修复有效。

每个 case 的必测路径：

1. 浏览器选择场景和默认变体，创建独立实验。
2. 点击制造问题并执行，断言 UI 展示了约定失败/阻塞，且证据可读取。
3. 点击诊断，断言原因引用真实证据与对应文件/阶段。
4. 点击修复，断言输入或系统状态有实际变化且 diff/状态变化可见。
5. 点击复验，断言对应机制实际通过；检查关键文件/进程/HTTP/数据库事实。
6. 检查前后结果、阶段时间、执行模式；刷新和切换 case 后仍能恢复记录。
